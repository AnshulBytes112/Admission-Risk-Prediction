# Configuration Architecture

This directory documents the configuration strategy for the **Emergency Admission Risk Prediction Using Big Data Analytics** project.

## Authoritative Configuration Source

Configuration is managed hierarchically to maintain single-source-of-truth consistency while allowing containerized, local, and CI/CD overrides:

1. **`.env.example`** (Version-controlled template): The authoritative reference containing all environment variables, their purpose, safe local development defaults, and valid value constraints.
2. **`.env`** (Host local override, git-ignored): Generated by copying `.env.example`. Used by Docker Compose and local developer shells. Never committed to version control.
3. **Environment variables**: Injected into Docker containers via `docker-compose.yml`.
4. **Application Fallbacks**: Built-in Python fallback defaults within `os.getenv("VARIABLE", fallback)` ensure graceful degradation if an optional environment variable is omitted.

## Configurable Parameters vs. Schema Contracts

To ensure architectural integrity, operational parameters are distinct from schema contracts:

- **Configurable Parameters**: Ports, directory paths, batch sizes, random seeds, row counts, thresholds, and hostnames are configurable via environment variables or CLI flags.
- **Fixed Schema Contracts**: Field names (`event_id`, `patient_id`, `heart_rate`, `spo2`, `admission_within_24h`, etc.) and Pydantic validation boundaries reflect the clinical schema specification and are intentional application contracts. Changing these requires deliberate schema migration, not dynamic configuration.
